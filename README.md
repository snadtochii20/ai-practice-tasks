# Практична робота з Node.js

## Тема
Docker, контейнеризація, JWT + RBAC, тестування Jest, AI code review та рефакторинг.

## Опис роботи
У роботі реалізовано простий Node.js/Express застосунок, який запускається на порту 3000.  
Проєкт містить Docker-інфраструктуру, авторизацію через JWT, перевірку ролей користувачів, unit-тести Jest та приклад AI code review з рефакторингом legacy-коду.

---

## Завдання 1. Docker та контейнеризація

### Що реалізовано

Для контейнеризації застосунку створено файли:

- Dockerfile
- docker-compose.yml
- .dockerignore

Dockerfile реалізовано як multi-stage build.  
У фінальному образі залишаються тільки production-залежності.  
Застосунок запускається не від root-користувача.

docker-compose.yml піднімає два сервіси:

- app — Node.js/Express застосунок;
- db — база даних PostgreSQL.

Для PostgreSQL додано volume `pgdata`, щоб дані зберігалися після перезапуску контейнера.

### Prompt, який використовувався

Підготуй Docker-інфраструктуру для простого Node.js Express застосунку, який працює на порту 3000. Потрібно створити multi-stage Dockerfile, у якому окремо встановлюються залежності, а у фінальному образі залишаються тільки production-залежності. Також потрібно створити docker-compose.yml для запуску застосунку разом із PostgreSQL, додати volume для збереження даних бази та створити .dockerignore.

### Коментар щодо змін після використання AI

Після використання AI було створено Dockerfile, docker-compose.yml та .dockerignore.

У Dockerfile було реалізовано multi-stage build. Спочатку встановлюються залежності, а у фінальному образі залишаються тільки production-залежності. Це дозволяє зробити образ меншим і безпечнішим.

Також було додано запуск застосунку не від root-користувача через команду USER node.

У docker-compose.yml було додано два сервіси: app для Node.js застосунку та db для PostgreSQL. Для бази даних створено volume pgdata, щоб дані не втрачалися після перезапуску контейнера.

У .dockerignore було додано node_modules, .git, .env, tests, coverage та інші файли, які не потрібно копіювати всередину Docker-образу.

### Підтвердження виконання

Для перевірки було виконано команду:

docker compose up --build

Після запуску контейнери app та db успішно стартували. У терміналі було видно повідомлення:

Server started on port 3000

## Завдання 2. Автентифікація та авторизація JWT + RBAC

### Що реалізовано

У файлі `src/app.js` реалізовано автентифікацію та авторизацію користувачів.

Створено endpoint:

POST /login

Він приймає:

{
  "email": "admin@test.com",
  "password": "admin123"
}

Якщо email та пароль правильні, сервер повертає JWT access-token з полями:

- userId
- role

Також реалізовано middleware `authenticate`, який перевіряє JWT-токен із заголовка:

Authorization: Bearer <token>

Якщо токен відсутній або неправильний, сервер повертає помилку 401.

Додатково реалізовано middleware `authorize(role)`, який перевіряє роль користувача. Якщо користувач не має потрібної ролі, сервер повертає помилку 403.

Захищений endpoint:

GET /admin

доступний тільки користувачу з роллю admin.

### Хешування паролів

Паролі не зберігаються у відкритому вигляді. Для хешування використано бібліотеку `bcryptjs`.

У коді використано:

bcrypt.hashSync("admin123", 10)

та перевірку пароля через:

bcrypt.compare(password, user.passwordHash)

### Підтвердження роботи

Для перевірки було виконано POST-запит на `/login`. У відповідь сервер повернув `accessToken`.

Також було перевірено endpoint `/admin`:

- без токена доступ заборонено, повертається 401;
- з токеном користувача admin доступ дозволено;
- для звичайного user доступ заборонено, повертається 403.

Отже, JWT-автентифікація та RBAC-авторизація працюють правильно.

## Завдання 3. Тестування Jest

### Що реалізовано

Для функції `calculateDiscount` створено unit-тести у файлі:

tests/discount.test.js

Тести перевіряють:

1. Знижку для `vip` клієнта.
2. Знижку для `regular` клієнта.
3. Випадок без знижки для невідомого типу клієнта.
4. Граничний випадок `price = 0`.
5. Помилку для від’ємної ціни через `expect(...).toThrow()`.

Також додатково створено тести для перевірки авторизації у файлі:

tests/auth.test.js

### Перевірка проходження тестів

Для запуску тестів була використана команда:

npm test

Після запуску всі тести виконались успішно.

У терміналі було отримано результат:

Test Suites: 2 passed, 2 total  
Tests: 9 passed, 9 total

### Використання AI

AI було використано для створення початкового варіанта тестів. Після цього тести були перевірені вручну.

AI міг не врахувати граничні випадки, тому додатково було перевірено:

- price = 0;
- від’ємну ціну;
- невідомий тип клієнта;
- перевірку помилки через toThrow.

Після ручної перевірки тести були запущені командою `npm test`, і всі вони пройшли успішно.

## Завдання 4. AI code review та рефакторинг

### Початковий код

У завданні був наданий legacy-код:

function process(d) {
  var r = [];
  for (var i = 0; i < d.length; i++) {
    if (d[i].active == true) {
      if (d[i].age > 18) {
        r.push(d[i].name + " - " + d[i].age);
      }
    }
  }
  return r;
}

### Prompt для AI code review

Проаналізуй цей JavaScript-код як code reviewer.  
Потрібно знайти проблеми з читабельністю, стилем, назвами змінних, вкладеністю умов, використанням var, нестрогим порівнянням та відсутністю перевірки вхідних даних.  
Після аналізу запропонуй рефакторинг без зміни поведінки програми.

### Знайдені проблеми

1. Назва функції `process` занадто загальна і не пояснює, що саме робить функція.
2. Назви змінних `d` та `r` неінформативні.
3. Використано `var`, хоча краще використовувати `const` або `let`.
4. Використано нестроге порівняння `==` замість `===`.
5. У коді є зайва вкладеність умов `if`.
6. Ручний цикл `for` можна замінити методами масивів `filter` та `map`.
7. Немає перевірки, чи вхідні дані є масивом.

### Відрефакторений код

Код винесено у файл:

src/refactor.js

Після рефакторингу використано:

- зрозумілу назву функції `getActiveAdultUsers`;
- методи масивів `filter` та `map`;
- строге порівняння `===`;
- перевірку `Array.isArray`;
- шаблонні рядки.

Поведінка програми не змінилася: функція повертає активних користувачів старше 18 років у форматі `"name - age"`.
